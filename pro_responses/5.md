I’d optimize the exact Windows forward-CV path in this order:

The current exact proxy is a 4-fold, non-overlapping 360-step expanding-window CV, and the promoted winner is `smoothed_stable_horizon_blend_last_target_recent_delta_k7_h13_pentaslice_h3_beta_up_v1` at `0.1451839276`. Each fold is large: train rows grow from about 2.88M to 4.73M, and each validation slice is about 606k–628k rows. The evaluator currently reads metadata up front, loads every fold’s train/validation frame before evaluation, rebuilds predictors baseline-by-baseline, predicts through a per-`ts_index` loop, and the predictor stack itself is heavy on pandas groupby/merge lookups. That is exactly the kind of CPU/parquet/pandas/DuckDB-bound path that will feel slower on Windows.     

## Quick wins

### 1) Add a full-frame fast path for the current baseline family

**Expected benefit:** Highest ROI. For the winner family, this is likely the single biggest pure-Python speedup because `SequentialInferencePipeline.predict()` currently sorts, groups by `ts_index`, copies each batch, predicts each batch separately, builds many tiny DataFrames, then concatenates them. The current baseline predictors are lookup-based and do not update state during validation batches, so that per-`ts_index` loop is overhead, not logic.   

**Why results stay identical:** Keep the same initial stable sort by `[ts_index, id]`, then call `transform_batch()` once and `predict_batch()` once on the full ordered frame for predictors that are explicitly marked “static over validation”. Since the current grouped mean, smoothed mean, linear blend, warm-start blend, and recent-delta predictors all use train-fit lookups and do not mutate from one validation timestamp to the next, whole-frame prediction is mathematically the same as batch-by-batch prediction over the same ordered rows.   

**Likely code touch points:** `09_SEQUENTIAL_DATA_HELPERS__sequential.py` for the fast path; small marker or protocol extension in `07_BASELINE_MODEL_IMPLEMENTATIONS__baselines.py` so current exact baselines opt into it cleanly. `12_PREDICTION_DRIVER__predict_baseline.py` would also benefit automatically because it uses the same pipeline.  

**Validation required:** Add a unit test that old per-batch path and new whole-frame path produce identical predictions on shuffled input. Then rerun the exact winner and compare fold prediction files and `summary.json` exactly, not just approximately.

### 2) Evaluate folds one at a time instead of preloading all folds

**Expected benefit:** High on Windows, especially if memory pressure is part of the slowdown. Right now the evaluator builds a `folds` list containing every fold’s `train_frame` and `validation_frame` before any scoring starts. With the current fold sizes, that is a lot of duplicate in-memory data before per-baseline fits and scored-frame merges even begin.   

**Why results stay identical:** This changes only evaluation order and lifetime of DataFrames. The folds, their boundaries, and the computations inside each fold stay exactly the same. The summary rows are still appended in the same fold order.  

**Likely code touch points:** `11_BASELINE_EVALUATION_DRIVER__evaluate_baselines.py` only. Replace the “build all folds, then iterate” pattern with “build fold spec, load one fold, evaluate, release, continue.” 

**Validation required:** Rerun the exact winner and confirm identical fold summaries, aggregate score, best baseline selection, and stress block.

### 3) Fuse the scoring path so each baseline/fold is aligned once

**Expected benefit:** Medium, low risk. Today the path does extra work: `evaluate_baseline()` predicts and merges once for the overall metric, then the main loop builds another scored frame with more merges, then stress summaries re-scan scored data again. That is several full-row joins and metric passes per baseline/fold.  

**Why results stay identical:** Build one ordered/aligned scored object per fold-baseline and derive overall, cold, warm, horizon, and watchlist summaries from that one alignment. The formulas and slices do not change; only redundant joins and passes disappear.  

**Likely code touch points:** `11_BASELINE_EVALUATION_DRIVER__evaluate_baselines.py`, mainly `evaluate_baseline()`, `summarize_scored_predictions()`, and the stress-block assembly.  

**Validation required:** Compare the old and new `summary.json` structurally and numerically, including the stress block.

### 4) Stop recomputing coverage summaries from fold train frames

**Expected benefit:** Medium-small, but easy and safe. `build_first_seen_lookup()` is already computed once from full train metadata. Coverage and cold-start summaries can be derived from first-seen timestamps for each key level instead of redoing `drop_duplicates()` on each fold train frame and merging again.  

**Why results stay identical:** “Seen in train by fold” is equivalent to `first_seen_ts <= train_end_ts`. That is the same logic now used for cold-start row annotation, just reused for coverage summaries too. 

**Likely code touch points:** `08_VALIDATION_AND_FORWARD_CV_UTILS__validation.py` and the call sites in `11_BASELINE_EVALUATION_DRIVER__evaluate_baselines.py`. 

**Validation required:** Exact equality of `cold_start_rows`, `cold_start_rate`, and every `coverage` block in the output summary.

## Medium-effort improvements

### 5) Cache fitted artifacts across baselines that share the same fitted subtree

**Expected benefit:** High when exact runs compare nearby variants, which this repo clearly does. The current winner follow-up in the exact summary compares closely related baselines, and in the registry the parent and promoted child differ only in top-level `beta_by_horizon` for the short-horizon recent-delta layer. That means the expensive fit artifacts below that point are the same, but the evaluator currently rebuilds and refits the whole nested tree per baseline.   

**Why results stay identical:** The cache would memoize deterministic fit outputs keyed by normalized config plus fold train boundary. For beta-only or alpha-only variants, reuse the same lookup tables and apply different coefficients only at prediction time. Same fitted data, same prediction math, fewer redundant fits.  

**Likely code touch points:** `06_BASELINE_REGISTRY_AND_WINNER_CONFIGS__baseline_registry.py` for config normalization and build hooks; `07_BASELINE_MODEL_IMPLEMENTATIONS__baselines.py` to separate fit artifacts from scalar prediction parameters where needed; `11_BASELINE_EVALUATION_DRIVER__evaluate_baselines.py` for fold-level cache lifetime.  

**Validation required:** Pick the exact winner comparison pair and verify identical per-fold predictions before and after caching. Add unit tests around config-hash collisions and cache invalidation by fold.

### 6) Replace merge-based predictor lookups with indexed reindex/lookups

**Expected benefit:** Medium to high once whole-frame prediction is in place. The current predictor stack repeatedly uses pandas `merge()` inside `predict_batch()` for lookup joins. With the winner stack, that means multiple joins for the same validation frame: smoothed mean levels, warm-start last target, recent delta, second warm-start layer, second recent delta layer. `merge()` creates large temporary DataFrames and moves columns around; `Series`/`MultiIndex.reindex()` is usually lighter for exact key lookup.   

**Why results stay identical:** In fit, store lookup outputs as Series indexed by the exact key tuple. In predict, construct the same key tuples from the batch frame and `reindex` them. Missing keys still become `NaN`, and fill/fallback logic remains unchanged. This is a representation swap, not a logic change.  

**Likely code touch points:** `WeightedGroupMeanRegressor`, `SmoothedWeightedGroupMeanRegressor`, `WarmStartLastTargetBlendRegressor`, and `RecentMeanDeltaRegressor` in `07_BASELINE_MODEL_IMPLEMENTATIONS__baselines.py`.   

**Validation required:** Unit tests on duplicates, unseen groups, and row-order preservation; then exact fold prediction equality on the winner.

### 7) Preload the narrow train frame once for winner-family exact runs

**Expected benefit:** Medium to high, depending on what `io.py` is doing today. The evaluator definitely reads full train metadata once, calls `get_max_ts_index()`, and calls `load_train_validation_window()` per fold. Since the 4-fold exact proxy covers the same train parquet repeatedly and the fold prefixes overlap heavily, there is clear repeated parquet work. For the current winner family, only context/group columns plus `y_target` and `weight` are needed; no feature matrix is used.   

**Why results stay identical:** Read the exact same required columns once, sort once, then slice by `train_end_ts` / validation window in memory. Same rows, same columns, same sort, same computations. This is just less repeated parquet scanning and less repeated DuckDB materialization.  

**Likely code touch points:** Primarily `ts_forecasting.io` plus a small mode switch in `11_BASELINE_EVALUATION_DRIVER__evaluate_baselines.py`. A clean version is “column planner + preload mode for exact grouped baselines; fallback to current per-fold loader for feature-heavy residual configs.” The uploaded docs already note DuckDB is the intended dataset-scale read layer. 

**Validation required:** Exact fold row counts, exact summary equality, and a Windows memory sanity check so the narrow preload does not create a different bottleneck.

## Larger refactors

### 8) Compile the selected baseline set into a shared evaluation DAG

**Expected benefit:** Highest upside for repeated local exact sweeps, but more engineering. The current evaluator treats each baseline independently, even when many baselines share the same deep base predictor. In this repo, the promoted family is explicitly layered: smoothed group mean + horizon blend, then warm-start overlays, then recent-delta overlays, then narrow follow-up tweaks. That structure is ideal for a compiled DAG that fits each unique subtree once per fold and emits predictions for multiple related baselines.   

**Why results stay identical:** The DAG would not approximate anything. It would simply evaluate the existing deterministic config tree once per unique node, then reuse those exact outputs where child configs overlap. Same fit order, same lookups, same arithmetic, less duplication. 

**Likely code touch points:** `baseline_registry.py` for normalized config-tree parsing, `baselines.py` for fit/predict node interfaces, and `evaluate_baselines.py` for orchestration.  

**Validation required:** Start with a two-baseline exact comparison where one baseline is a strict child variation of the other, then expand to the full winner shortlist and compare every prediction file and summary field.

### 9) Refactor I/O around “materialize once, slice many”

**Expected benefit:** High on Windows for exact reruns, but this belongs after the cheap wins because it touches more plumbing. The evaluator’s current pattern strongly suggests repeated parquet scans and repeated fold materializations. A dedicated “exact CV materializer” that builds one narrow Arrow/DuckDB temp relation and slices train/validation windows from that relation would reduce both I/O and pandas conversion churn.  

**Why results stay identical:** This is still deterministic filtering on the same raw parquet rows and same sort keys. Only the storage boundary changes. 

**Likely code touch points:** mostly `ts_forecasting.io`, with a thin interface in `evaluate_baselines.py`. The docs already position DuckDB as the dataset-scale read layer, so this fits the existing design. 

**Validation required:** Structured equality of all fold DataFrames against the current loader on a smoke subset, then exact full-summary equality on the winner run.

## What I would do first

On your Windows box, my implementation order would be:

1. **Static whole-frame prediction fast path**
2. **Fold streaming instead of preloading all folds**
3. **Single-pass scoring/stress assembly**
4. **Shared fit-artifact cache for related baselines**
5. **Lookup reindexing instead of merge**
6. **One-read narrow preload mode for the winner family**

That order gives the best speedup-to-risk ratio while keeping exactness easiest to prove. It also targets the exact hot spots you called out: `evaluate_baselines.py` orchestration, validation merges, repeated predictor rebuilds, repeated parquet scans, and the per-`ts_index` loop.    

The one recommendation I would *not* make first is a broad I/O rewrite in the dark, because the current evaluator already has several obvious Python-side inefficiencies that are easier to remove and easier to verify exactly. The fastest safe path is to first eliminate redundant prediction batching and redundant refits, then decide how much parquet work is still dominating.
