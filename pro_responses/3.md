## 1. Core idea

**A strict-OOF, feature-conditioned residual stack on top of the current incumbent**, starting with **short horizons `1` and `3` only**.

Concretely: keep the current winner as the base predictor, generate **out-of-fold / prefix-safe base predictions on train**, define a leakage-safe residual target from those predictions, then train a **small regularized residual model** that maps row features plus stable context to a correction. At inference, the final prediction is:

`current_incumbent_prediction + learned_residual_correction`

This is already partially scaffolded in the repo through the residual tooling: prefix-only residual scales, OOF residual pools, and regularized residual learners are implemented and explicitly exclude `feature_al` and keep `aggregate_overall_score` canonical.   

## 2. Why this is truly different from the exhausted family

The promoted family is a **deterministic grouped-statistics stack**: smoothed stable-group means, fixed linear blends, exact warm-start last-target overlays, and fixed recent-vs-full-history mean deltas with hand-written activation rules. That family has been widened and micro-tuned repeatedly, and both the short-horizon drift branch and long-horizon warm-overlay branch are now documented as near-plateaued or exhausted.  

What I am proposing is not another overlay, not another alpha/beta sweep, and not another recent-delta variant. It is a **learned supervised correction model** that uses row features and context to predict residual error. That is a different modeling family in both representation and training procedure.

The repo evidence supports that distinction. The current winner is `smoothed_stable_horizon_blend_last_target_recent_delta_k7_h13_pentaslice_h3_beta_up_v1`, which is still inside the recent-delta / warm-overlay stack.   
By contrast, the residual code path builds an explicit model over residual targets with imputation, scaling, categorical encoding, and regularized learners such as Ridge, Huber, or HistGBM.  

## 3. Why it might improve the current failure pattern

The current winner still has a very specific unresolved pattern:

* test is extremely cold-start below `(code, sub_category, horizon)`: `89.12%` of test rows are unseen at `(code, sub_code)`, while `(code, sub_category, horizon)` has full coverage. 
* the weakest slices remain concentrated in **horizons `1` and `3`**, especially around `DPPUO5X2`, `PZ9S1Z4V`, and `PHHHVYZI`.  
* even after the final short-horizon ratchet, the combined `fold_02_03` stress block is still only `0.08657`, and its aggregate warm-start score is still `0.0`. 
* per horizon, the winner is still far weaker on `1` and `3` than on `10` and `25`: about `0.03405` on horizon `1`, `0.05967` on horizon `3`, versus `0.12024` and `0.17634` on `10` and `25`.  

That matters because the current family mainly adjusts **group means and recent drifts**. It has very limited ability to exploit **row-level feature structure** when the same `(code, sub_category, horizon)` bucket contains heterogeneous rows, especially in cold-start conditions where `sub_code` history is unavailable.

A feature-conditioned residual model is one of the few leakage-safe ways to attack exactly that gap: leave the strong grouped base intact, then learn when individual rows should move above or below that base using only train-time/OOF information.

The repo evidence also says this family is not fantasy: residual-on-base already showed real numerator reductions, even though earlier versions were built on weaker bases and narrower slices. The best raw tri-slice residual branch improved the smoothed baseline from `0.1119478178` to `0.1128626342`, while the strict-OOF normalized replacement path was cleaner but weaker at `0.1123268577`.   
So the evidence says “feature-conditioned residuals have some signal,” but they have not yet been tried as a clean second stage on top of the **current best incumbent**.

I would implement this as a new residual family, reusing the existing residual scaffolding rather than inventing a parallel pipeline.

### A. New family name

Add a new residual config family such as:

`ridge_oofnorm_incumbent_h13_pentaslice_tw720_s003_q85_v1`

The point is not the exact name; the point is that it is clearly an **incumbent-based OOF residual** family, not another baseline overlay.

### B. Base model

Use the current winner config as the base predictor:

`RECENT_DELTA_K7_H13_PENTASLICE_H3_BETA_UP_V1_CONFIG`
from the baseline registry.  

### C. Training target construction

Reuse the exact logic already present in `scripts/evaluate_residual_models.py`:

1. Load saved fold predictions for the base baseline.
2. For each fold, attach prefix-only residual scales using:

   * `build_residual_scale_lookup`
   * `attach_residual_scales`
   * `compute_normalized_residual_targets`
3. Build training pools only from earlier OOF folds whose max `ts_index` is `<= train_end_ts` for the current fold.

That logic is already in the residual driver and is leakage-safe by construction.    

### D. Features

Use the existing `detect_residual_feature_columns(...)` path, with these rules:

* **ban `weight`**
* **ban `feature_al`**
* keep context columns already used in residual code:

  * `code`
  * `sub_category`
  * `horizon`
  * `ts_index`
  * causal numeric features from train columns
* optionally include the base prediction itself as a numeric feature in the new family

The codebase already bans `feature_al` in the residual driver and registry examples.  
`weight` is explicitly scoring-only in the project rules.  

### E. Model form

Start with **Ridge** only.

Do not start with HistGBM or broad model sweeps. The docs say a sampled feature-only HistGBM probe failed to beat zero, while Ridge residuals were the only residual path that consistently produced small gains.

* horizons: `[1, 3]`

I would prefer **all five sub-categories on horizons `1` and `3`** for the first real test, because the current winner already proved the whole pentaslice short-horizon branch matters, and the failure is no longer confined to one tiny bundle.
