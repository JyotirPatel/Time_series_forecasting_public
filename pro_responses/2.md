## 2) Clipped / gated recent-delta on horizons 10 and 25

### Exact features / statistics to compute

This should extend the existing `RecentMeanDeltaRegressor`, not replace it. It already computes:

* `full_weighted_target_sum`
* `full_weight_sum`
* `full_row_count`
* `recent_weighted_target_sum`
* `recent_weight_sum`
* `recent_row_count`
* `full_mean`
* `recent_mean`
* `delta = recent_mean - full_mean`

all at `(code, sub_category, horizon)`. 

Add:

* `abs_delta`
* `clip_abs_by_horizon` learned from the **training prefix only**, e.g. quantiles of `abs_delta` within each horizon
* optional `apply_rules` mask, parallel to warm rules, to restrict which `(code, sub_category, horizon)` groups get delta applied
* optional `beta_by_horizon`
* optional `min_recent_weight_sum` guard in addition to `min_recent_rows`

I would extend the class roughly like this:

```python
@dataclass
class RecentMeanDeltaRegressor:
    ...
    beta_by_horizon: dict[int, float] | None = None
    clip_quantile_by_horizon: dict[int, float] | None = None
    apply_rules: list[dict[str, object]] | None = None
    min_recent_weight_sum: float = 0.0
```

Repo-specific point: because the stable level `(code, sub_category, horizon)` has full test coverage, this branch is exactly aligned to your cold-start geometry. 

### Train / validation protocol

Use the same four-fold forward CV and the new stress report from Experiment 1.

Implementation order:

1. Build delta variants **on top of** `smoothed_stable_horizon_blend_last_target_rules`, not directly on top of the K7 stack.
2. Compare them first against `smoothed_stable_horizon_blend_last_target_recent_delta_v1`.
3. Only after a delta variant wins, wrap that winner with the outer K7/OSJL/X9 warm overlays.

That keeps attribution clean. The docs already show the path was:

* `smoothed_stable_horizon_blend`
* `..._last_target_rules`
* `..._recent_delta_v1`
* `..._recent_delta_k7_v1`  

### Inference-time causal rules

At test time:

* fit the base predictor on train `1..3601`
* compute `delta_lookup_` **once** from train only
* compute clip thresholds **once** from train only
* during prediction, `SequentialInferencePipeline` already processes rows in nondecreasing `ts_index`; `predict_batch` just merges the frozen lookup and adds `beta * clipped_delta` where a stable group exists. No future test rows are touched.  

### Ablations to run

Keep the grid small:

* `recent_window`: `120`, `180`, `240`
* `min_recent_rows`: `50`, `100`
* `beta_by_horizon`:

  * horizon `10`: `0.05`, `0.08`, `0.10`
  * horizon `25`: `0.10`, `0.15`, `0.20`
* `clip_quantile_by_horizon`:

  * horizon `10`: `0.70`, `0.80`, `0.90`
  * horizon `25`: `0.80`, `0.90`, `0.95`
* `apply_rules`:

  * none
  * only `OSJL3A7Y` / `X9BZ68VQ`
  * only high-energy `10/25` sub-category slices from the watchlist

Proposed config names:

* `smoothed_stable_horizon_blend_last_target_recent_delta_clip_v1`
* `..._clip_osjlx9_v1`
* `..._clip_hbeta_v1`

### Failure modes to watch

* Because this delta is applied at stable-group level, it can change **cold rows too**, so a warm-row gain can still hurt `aggregate_cold_start_score`.
* Too-low clip quantiles will erase the useful drift signal you just found on `10/25`.
* Too-short `recent_window` can reintroduce the “recent-window grouped averages regressed” behavior already logged in the repo.
* If you apply this after the outer warm overlay instead of before, attribution gets muddy and you can accidentally double-correct the same slices.  

### Files / modules to change

* `src/ts_forecasting/baselines.py` — extend `RecentMeanDeltaRegressor`
* `scripts/evaluate_baselines.py` — add new delta configs
* `scripts/predict_baseline.py` — add the same config registry entry, unless you centralize configs
* `tests/test_baselines.py` — unit-test clip/gating behavior and frozen lookup semantics
* `documentation.md` — record winning grid and stress behavior

## 3) Expand exact warm overlays for `OSJL3A7Y` and `X9BZ68VQ` on horizons 25 and 10

### Exact features / statistics to compute

This one mostly reuses existing logic. `WarmStartLastTargetBlendRegressor` already:

* fits a base predictor
* builds `last_target_lookup_` from the last training target per exact group
* supports rule conditions on any subset of `GROUP_COLUMNS`, including `code`, `sub_category`, and `horizon`
* blends as `(1-alpha) * base + alpha * last_target` for matching warm rows. 

So the additional statistics you need are not new model features; they are **candidate-rule diagnostics**:

* `warm_rows`
* `warm_denom_sum`
* base slice score
* last-target-only slice score (`alpha=1` diagnostic)
* alpha sweep result on each candidate slice

I would candidate-filter using the attached error analysis, which already flags these high-energy misses:

* `OSJL3A7Y × {DPPUO5X2, PZ9S1Z4V, PHHHVYZI} × {10,25}`
* `X9BZ68VQ × {DPPUO5X2, PHHHVYZI} × {10}`
* `X9BZ68VQ × {DPPUO5X2, PHHHVYZI, PZ9S1Z4V, NQ58FVQM} × {25}` 

### Train / validation protocol

Do this in narrow stages, not one huge union config:

1. `OSJL h25` only
2. `X9 h25` only
3. `OSJL h10` only
4. `X9 h10` only
5. combine only the winners

Base predictor for this experiment:

* if Experiment 2 has a clear winner, use that as the base
* otherwise use current incumbent `smoothed_stable_horizon_blend_last_target_recent_delta_k7_v1` at `0.1450306103` 

I would not add all OSJL/X9 rules at once. The docs explicitly warn about “without reopening fold 02 damage,” so you want attribution by code and by horizon. 

### Inference-time causal rules

At test time:

* build `last_target_lookup_` from training rows only
* apply the overlay only if the exact `(code, sub_code, sub_category, horizon)` group was seen in train
* if unseen, return the base prediction unchanged

That is naturally causal and safe. It also means this branch is **warm-only**; it will not rescue the 89.12% cold exact groups, which is why Experiment 1’s stress report matters.  

### Ablations to run

Keep alphas small because these rows are already getting the generic warm overlay underneath.

Start with:

* horizon `10`: `alpha ∈ {0.03, 0.05, 0.08}`
* horizon `25`: `alpha ∈ {0.05, 0.08, 0.12, 0.15}`

Rule bundles to try:

* `OSJL_H25_WARM_RULES_V1`
* `X9_H25_WARM_RULES_V1`
* `OSJL_H10_WARM_RULES_V1`
* `X9_H10_WARM_RULES_V1`
* `OSJL_X9_H1025_WARM_RULES_V1` only after the singles are tested

Practical config shape:

```python
OSJL_H25_WARM_RULES_V1 = [
    {"code": "OSJL3A7Y", "horizon": 25, "sub_category": "DPPUO5X2", "alpha": 0.08},
    {"code": "OSJL3A7Y", "horizon": 25, "sub_category": "PZ9S1Z4V", "alpha": 0.08},
    {"code": "OSJL3A7Y", "horizon": 25, "sub_category": "PHHHVYZI", "alpha": 0.08},
]
```

and likewise for `X9BZ68VQ`.

### Failure modes to watch

* No effect because the slice is mostly cold at exact-group level.
* Over-blending due to stacking on top of the existing generic warm rules and the outer K7 overlay.
* Winning on fold `01/04` but worsening `02/03`, which is the exact pattern you want to avoid.
* Too many overlapping rules: `WarmStartLastTargetBlendRegressor` applies matching rules sequentially, so if a row matches multiple outer rules you can unintentionally compound the blend. Keep the new rule bundles mutually exclusive by `code/sub_category/horizon`. 

### Files / modules to change

* `scripts/evaluate_baselines.py` — add new rule lists and stacked configs
* `scripts/predict_baseline.py` — same config registry entry
* `documentation.md` — log which code/horizon overlays helped or failed
* optional: `scripts/analyze_validation_errors.py` or a tiny new helper to alpha-sweep saved fold predictions before you materialize the final config

You probably **do not** need to change `src/ts_forecasting/baselines.py` for this experiment, because code-filtered warm rules are already implemented and proven by the K7 stack.
